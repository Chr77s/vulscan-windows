# Round 7 — UI/UX Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give VulnScan's DevTools panel the UI capabilities Round 6 built the data for but never surfaced — a request/response traffic viewer, an attack-surface map, a live per-module activity log, working triage buttons, a full 30-module picker, and a light theme — without a framework rewrite.

**Architecture:** The dashboard (`panel.html`/`panel.js`, vanilla JS/CSS, cards + KPI + donut + diff) is extended, not rewritten. Two small plumbing gaps discovered while grounding this plan against the merged Round 6 code are fixed first, since every later task depends on one of them: `service-worker.js`'s `ensureFinding()` silently discards every backend-computed field it doesn't explicitly whitelist (including Round 6's new `evidenceRequest`/`evidenceResponse`, and — pre-existing, not a Round 6 regression — the backend's own per-finding `cvssBase`/`cwe`/`owasp`), and `runActiveModules()` never captures the backend's `discovery` object at all. Both become additive fixes (Tasks 1 and 4), not redesigns.

**Tech Stack:** Vanilla JS (ES modules) + HTML/CSS, Chrome MV3 `chrome.storage.local` + `chrome.runtime` messaging, Flask (two small backend additions: an engine-level per-module log, and a fuller `discovery` payload). No new dependency, no test framework introduced for the extension (per spec non-objectives) — verification is `node --check` for syntax plus a manual load in real Chrome, matching the project's existing convention.

**Spec:** [docs/superpowers/specs/2026-10-14-vulnscan-premium-hardening-design.md](../specs/2026-10-14-vulnscan-premium-hardening-design.md) §3 (Round 7).

## Global Constraints

- The existing dashboard (cards, KPI strip, donut, Historique, Diff tabs) is preserved exactly — this plan adds tabs and sections, it does not restructure what's there (spec §3, "on ajoute des vues, pas une refonte").
- No framework (React/Vue) and no test framework for the extension (spec §1 non-objectifs, reaffirmed in §3.7).
- Severity color semantics (`--critical`/`--high`/`--medium`/`--low`/`--info` hues) stay identical between dark and light theme — only backgrounds/text invert (spec §3.6).
- Streaming is optional, not required: if the NDJSON/live-per-module approach adds too much risk, the fallback is a post-hoc activity log rendered once the (still-blocking) `/scanner/run` call returns — explicitly permitted by spec §3.3, "pas de régression" either way.
- Triage buttons must work without any backend round-trip for display (the panel's primary data source for the open scan is `chrome.storage.local`, not a live backend re-fetch) — writing through to SQLite (already built in Round 6) is for cross-session/backend consumers, not a dependency for the UI to show the new status.

## Review Focus

- **`ensureFinding`'s wider pass-through swallowing a client-side (content-script) finding's shape.** Client-sourced findings never carry `evidenceRequest`/`cvssBase`/etc., so spreading `...f` must not break their existing default-filled rendering — Task 1 must verify a client-sourced finding (no extra fields) still produces the exact same `base` object as before.
- **A failed triage PATCH silently corrupting local state.** If `PATCH /history/triage/<id>` fails (network/backend down), the local `chrome.storage.local` update must not happen — a reasonable person clicking "Confirmé" expects either a visible change or a visible error, never a silent desync between what the button shows and what's actually stored.
- **An explicitly-empty custom module selection silently falling back to "run everything anyway."** A user who unchecks every module in the new picker expects zero modules to run, not a silent fallback to the old fixed list — Task 7 must distinguish "never configured" (`customModules` absent) from "configured to nothing" (`customModules: []`).
- **Light theme breaking severity legibility.** Toggling theme must not make a `critical`-severity badge unreadable (e.g. red-on-white-on-red) — Task 8 must keep text/background contrast correct in both themes for every `badge-*`/`sev-*` class.
- **A discovered form's field values rendered verbatim in the new Surface tab.** The crawler captures each `<input>`'s HTML `value` attribute (not user-typed data), but a security tool displaying raw form field values by habit is the kind of thing that should be deliberate, not accidental — Task 4 renders field `name`/`type` only, never `value`.

## Task 1: Fix `ensureFinding` to pass through backend-computed fields

**Why this task exists:** verified directly in the merged code (not assumed): `service-worker.js`'s `ensureFinding(f, url)` builds `base` as a hand-picked whitelist of 13 keys, so `f.evidenceRequest`/`f.evidenceResponse` (Round 6) are silently dropped before `enrichFinding(base)` ever sees them — Task 3 (Traffic tab) has nothing to render without this fix. Also discovered in the same read-through, pre-existing and unrelated to Round 6: the backend's own precise per-finding `cvssBase`/`cvssVector`/`cwe`/`owasp`/`impact`/`references` are discarded the same way, silently replaced by `taxonomy.js`'s generic per-type fallback — `enrichFinding`'s `v.cvssBase ?? tax.cvssBase` pattern only works if `v.cvssBase` actually reaches it.

**Files:**
- Modify: `extension/src/background/service-worker.js:424-442` (`ensureFinding`)

**Interfaces:**
- Modifies: `ensureFinding(f, url)` — same signature and return value shape as today, but the returned object now carries every key present on `f` (via spread), not just the 13 previously whitelisted ones. Every later task that reads a finding's `evidenceRequest`/`evidenceResponse`/`triageStatus` (Tasks 2, 3, 6) relies on this.

- [ ] **Step 1: Make the change**

Replace the `base` object literal (currently `{ id: f.id || ..., detectedAt: f.detectedAt || ..., ... }`, 13 keys) with one that spreads `f` first, then applies the same 13 defaults on top — so every other key on `f` (not just the 13) survives into `base`:

```javascript
function ensureFinding(f, url) {
  const base = {
    ...f,
    id: f.id || crypto.randomUUID(),
    detectedAt: f.detectedAt || Date.now(),
    scanMode: f.scanMode || "backend",
    severity: f.severity || "info",
    type: f.type || "unknown",
    url: f.url || url,
    description: f.description || "",
    recommendation: f.recommendation || "",
    parameter: f.parameter || "",
    evidence: f.evidence || "",
    payload: f.payload || null,
    detectionMethod: f.detectionMethod || "passive-dom-analysis",
    confidence: f.confidence ?? 80,
    source: f.source || "backend",
  };
  return enrichFinding(base);
}
```

The 13 explicit keys are unchanged in name, default value, and evaluation order relative to each other — only the leading `...f` is new, and it must come first in the object literal so the explicit keys below it still win when `f` already had a value for one of them (object literal property order: later keys override earlier ones of the same name).

## Task 2: Client-side triage write-through (message type + storage update)

**Files:**
- Modify: `extension/src/background/service-worker.js:77-106` (`handleMessage`'s `switch`)

**Interfaces:**
- Produces: a new message type `SET_TRIAGE`, payload `{ scanId: string, findingId: string, status: "unreviewed"|"confirmed"|"false_positive", note?: string }`. On success: `PATCH {cfg.backendUrl}/history/triage/<findingId>` (Round 6, `routes/history.py`) is called with body `{status, note}`; if that call resolves with `ok`, the matching finding inside `chrome.storage.local.scanHistory[].vulnerabilities` (found by `s.id === scanId` then `v.id === findingId`) gets `triageStatus`/`triageNote` set directly on the stored object, and the handler returns `{ success: true }`. If the PATCH fails or the backend is unavailable, storage is left untouched and the handler returns `{ success: false, error: <message> }` — Task 6's button click handler uses this to decide whether to update the card's own in-memory state.

- [ ] **Step 1: Implement**

Add a case to `handleMessage`'s `switch` (alongside the existing `VULN_FOUND`/`EXPORT_REPORT` cases):

```javascript
case "SET_TRIAGE": {
  const { scanId, findingId, status, note } = message.payload || {};
  const { config } = await chrome.storage.local.get("config");
  const cfg = { ...DEFAULT_CONFIG, ...(config || {}) };
  try {
    const r = await fetch(`${cfg.backendUrl}/history/triage/${findingId}`, {
      method: "PATCH",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ status, note }),
      signal: AbortSignal.timeout(5000),
    });
    if (!r.ok) return { success: false, error: "HTTP " + r.status };
  } catch (e) {
    return { success: false, error: e.message };
  }
  const { scanHistory } = await chrome.storage.local.get("scanHistory");
  const history = scanHistory || [];
  const scan = history.find(s => s.id === scanId);
  const finding = scan && scan.vulnerabilities.find(v => v.id === findingId);
  if (finding) {
    finding.triageStatus = status;
    finding.triageNote = note || "";
    await chrome.storage.local.set({ scanHistory: history });
  }
  return { success: true };
}
```

(This sits as one more `case` inside the existing `switch (message.type)` block — no change to the `switch`'s structure or the other cases.)
